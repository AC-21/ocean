# Harborline Release Blocker Ledger

Last updated: 2026-06-07

This ledger captures anything that prevents Harborline from becoming a playable
premium desktop release candidate. Use it when a finding is more concrete than
general taste feedback: it needs a surface, reproduction or evidence, severity,
status, and proof required to close.

## Severity

- `S0` Release blocker: the game cannot ship until this is resolved.
- `S1` High-value polish: not necessarily release-blocking, but it materially
  affects fun, comprehension, trust, or premium feel.
- `S2` Watchlist: useful follow-up, balance concern, or post-slice improvement.

## Status

- `Open`: known problem with no accepted fix yet.
- `In Progress`: actively being fixed or verified.
- `Needs Evidence`: likely improved, but proof is incomplete.
- `Closed`: fixed and verified with the exit proof recorded.

## Intake Rule

Every new issue should be written in this shape:

- Finding: one sentence describing the player-facing problem.
- Surface: the screen/system where the problem appears.
- Reproduction or evidence: exact steps, command output, browser URL, playtest
  quote, screenshot path, or report path.
- Exit proof: the command, browser smoke, playtest scorecard, packaged-app
  smoke, or visual artifact that would prove closure.

## Closure Checklist

Before marking any blocker or polish item `Closed`:

1. Confirm the issue still reproduces or identify the exact change that fixed it.
2. Run the narrowest useful automated test for the affected system.
3. Run `npm run verify` unless the change is documentation-only.
4. Run browser smoke or a manual in-app browser check when the player surface
   changed.
5. Record the command, browser URL, report path, screenshot path, or playtest
   scorecard that proves closure.
6. Update `MASTER_TASK_LIST.md` when the closure changes roadmap status.
